## Phase Goal

**As a** the owner, **I want to** have an approved scan processed by real Echo-3 exactly once, inside my budget, and retry a retryable failure only after re-confirming the cost, **so that** a paid run never double-charges and never wastes money on a bad capture.

<objective>
Vertical slice 7 (server side of retry + alert surfacing): the API exposes `retryable`, `submit_attempt`, `frame_count` and `budgetAlert`, and `POST /v1/worlds/:id/retry` turns an explicit fresh approval into exactly one new attempt with a new key.

Purpose: LIB-02 / success criterion 3 backend half; PROC-05's "retry needs a new explicit approval"; OPS-06 in-app surfacing data (D-13). The app (06-03/06-05) already renders this contract.
Output: retry.ts `applyRetry` + `ledgerClear`, worlds.ts route + serializer fields + list budgetAlert, scans.ts quote budgetAlert, tests.
</objective>

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-06-28 | Elevation | retry another user's world | mitigate | requireUserId + findOwnedWorld → 404 for non-owners (V4 ASVS) |

| T-06-30 | Tampering (financial) | duplicate / concurrent retries creating two paid attempts | mitigate | Idempotency-Key replay via world_attempts.client_request_id; unique (world_id, attempt); conditional update on submit_attempt; enqueue in the same tx |
| T-06-31 | Tampering (financial) | approval below current price | mitigate | server re-quotes and refuses approved < quote; pipeline's QUOTE_ABOVE_APPROVAL check still applies at submit |
| T-06-32 | Denial of service / financial | retry spam | mitigate | create-bucket rate limit (RATE_LIMIT_CREATE_MAX) + budget caps under advisory lock |
| T-06-33 | Input validation | body/header | mitigate | zod strict body (int, positive, ≤ 2e9) and z.guid() key |
| T-06-34 | Information disclosure | logs | mitigate | log world id only; never key/body/URL |
